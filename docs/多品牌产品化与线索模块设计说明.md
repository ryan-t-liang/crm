# 多品牌产品化与线索模块设计说明

## 结论

这套 CRM 可以复用为多品牌产品，但不能“零配置直接套用”。页面和核心域不需要为新品牌复制；新品牌至少需要品牌配置、表单 Schema/Version、枚举/产品目录、Consent 文案与版本、权限范围、HQ 映射及 Connector 配置。

## 稳定 Canonical Core

- **Customer**：跨品牌 Person 主体，以已验证手机号作为本地主要联系方式；不因姓名或未验证 Email 自动合并。
- **Brand Membership/Profile**：品牌会员 ID、注册姓名、品牌 Email、地址、国家语言、偏好、腕表持有、注册来源/时间。
- **Identity**：手机号、品牌/公众号作用域 OpenID、Open Platform 作用域 UnionID；页面默认脱敏。
- **Consent**：Brand + Purpose + Channel + Status + Policy/Terms Version + Evidence 的追加历史，不以单个布尔值替代底层语义。
- **Lead**：一条 Lead 只属于一个品牌，可不关联 Customer；保留标准化字段与原始提交快照。
- **Event/Journey、Note、Audit**：独立记录业务事件、人工备注和不可抵赖的操作轨迹。
- **HQ Link/Outbox/Attempt**：品牌/外部系统级映射、可靠投递、幂等和每次调用记录。

## 配置层

1. `brands`：code、名称、顺序、主题 token、启用状态。
2. `form_definitions`：brand、object_type、form_key、version、schema_json、policy/terms version、生效时间。
3. 字段：类型、必填、枚举、长度、正则、localOnly、可见性和标准化映射。
4. 产品与枚举：SKU、系列、国家、语言、首选联系渠道、购买方式。
5. Consent：展示文案、Purpose、Channel、Policy Version、证据捕获规则。
6. RBAC：Permission 与 Role；账号的品牌范围使用关系表，不使用组合枚举。
7. Connector：Endpoint、认证方式、字段映射、成功语义、重试和限速。

品牌主题/文案、表单配置、业务数据和 Connector 分离。当前 GP/UN 差异集中于 Brand/Form/Gateway Config，会员和线索页面共享同一渲染与服务代码。

## 线索模块边界

- 在线表单、后台新增和外部 API 均先通过相同 Form Definition 与 Canonical Service。
- `source/submissionMode` 只说明来源，不改变字段语义和校验路径。
- Lead 可选关联 Customer；非会员保持 `customer_id=null`，界面显示 `-`。
- 本地接受与 Gateway 投递解耦：先事务保存 Lead/Consent/Journey/Outbox/Audit，再由 Worker 投递。
- 手动同步与自动同步复用同一 Outbox、幂等键、Retry Policy 和 Attempt 记录。
- 当前系统只单向提交 Purchase Intent Lead，不接收 HQ 跟进进度。

## 新品牌接入步骤

1. 创建 Brand 与主题/文案配置。
2. 建立 Customer/Lead 表单版本，定义必填差异和 Consent 版本。
3. 导入国家、语言、渠道、SKU/系列等枚举。
4. 配置角色可访问的品牌范围。
5. 完成该品牌 Connector：Endpoint、认证、字段/枚举、错误、成功与限速映射。
6. 运行 Payload 契约、权限隔离、模板、导入、Outbox 与浏览器 UAT。
7. 经业务和运维授权后，以独立测试 Key 运行 Live Test，再逐步放量。

## 可以复用的前提

- 新品牌共享 Customer、Brand Membership、Consent、Lead、Audit 和 Outbox 核心域。
- 业务差异能由 Form/Field/Enum/Consent/Visibility/Mapping 配置表达。
- HQ 接口能以现有 Connector SPI 的 Payload、认证、响应、重试边界扩展。

## 不能零配置套用的边界

- HQ 模型、主键/去重、审批流或回写机制不同。
- 数据驻留、跨境传输、删除/匿名化期限不同。
- Consent Purpose、证据、撤回或法域要求不同。
- 需要多阶段销售 Pipeline、双向 HQ 同步或跨品牌共享 Contact。

这些情况需要新的 Connector、规则或域扩展，不能用页面写死品牌判断来规避。

## MVP 分期

- **MVP 1**：Customer/Brand Profile、Lead、Consent、RBAC、单向 Outbox、导入导出、审计。
- **MVP 2**：真实 Gateway 联调、监控告警、Dead Letter 运维、对象存储。
- **MVP 3**：新品牌配置后台、产品目录服务、分布式 Worker、数据治理。
- **后续**：仅在 HQ 合同确认后增加回调/状态回写、Contact Link 与删除/匿名化工作流。

## 主要风险

- 将 Gateway HTTP 202 误写为 HQ 已完成。
- 以 Email/姓名错误合并跨品牌 Customer。
- 将 Consent 压缩为一个布尔值或丢失 Policy Version/Evidence。
- 将 accessKey 放入前端、Outbox、Audit 或日志。
- 多 Worker 下没有分布式限速/租约导致超过 10 次/分钟或重复投递。
- 新品牌绕过配置层，在页面和服务中散落品牌条件分支。
