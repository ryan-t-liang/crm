# 营销活动模块 V1

实施日期：2026-09-17。基于当前 `codex/kivisense-product-prototype` 工作区，基线 `cc8e492f4a2409c55f10b3a16199eedeb652ce32`，不回退、不自动拉取或替换分支。按用户新增营销活动提示词实施；上一份概览任务“不开发营销活动”的范围已被本次新增任务扩展，三个概览不再次设计。

## 入口与使用

以现有 HQ 演示账号 Ryan 进入“MEMBER & BRAND → 营销活动”，主入口只有一个：

| 页面 | Hash 路由 | 数据与动作 |
| --- | --- | --- |
| 活动管理 | `#marketing` | 搜索、授权品牌、状态、举行日期筛选及分页；新建 / 编辑 / 发布 / 暂停 / 恢复 |
| 奖品库 | `#marketing/prizes` | 复用中性定义；名称、说明、图片及默认领取方式，不是销售 Product |
| 预约记录 | `#marketing/bookings` | 同一 Store 中的 ACTIVITY / PRIZE 两类记录，可按活动 / 业务类型筛选 |
| 核销工作台 | `#marketing/redemption` | 输入真实演示码或从预览“模拟扫码”带入，先识别，再确认具体动作 |
| 活动详情 | `#marketing/activity/<activityId>` | 概览 / 活动配置 / 场次与预约 / 参与名单 / 抽奖与奖品 / 核销记录六个 Tab |
| 用户预览 | `#marketing/preview/<activityId>/<userId>` | 引用当前可见品牌 user，与后台完全共用营销数据；不是独立小程序 |
| 凭证识别 | `#marketing/redemption/<encodedCredential>` | 只预填不自动执行；没有扫码摄像头或微信服务 |

例如 `activity-demo-1` 对应预约工坊，userId 必须从现有品牌档案中选择。同名或相同手机号不能代替引用。会员详情新增只读“营销活动”Tab，可进入该活动与相同 user 的预览。

沿用 Semi Tabs、Table、SideSheet、Modal、Input / Select / InputNumber / Switch、Banner / Empty、既有 DetailWorkspace / PageHeader / DataList。新 CSS 仅为模块表单、凭证、指标等组合布局；不引入新 UI 框架。唯一新增运行依赖 `qrcode-generator@2.0.4` 是 MIT 二维码编码工具，二维码真实编码同一个可输入的随机演示凭证，不含手机号 / 会员资料。

## 不变的业务边界

- 纯前端，不新增 SQL 表、数据库、后端、真实鉴权、队列、部署架构、微信 / HQ 接口。
- 销售仍为 Lead → Qualified → Convert to Deal → Won/Lost，无 Opportunity / 金额。营销报名、机会、中奖、核销从不生成 Lead / Deal / 购买意向。
- customer / user / user_profile / user_purchase_intent 的关系不变；不改手机号匹配、UnionID、跨品牌关联动作，也不新增 Person / Membership。
- 销售和会员 Store、旧键、加载与重置代码不改。会员详情仅增加只读入口；概览读取层的 SQL 展示适配见 `SOWIND_MEMBER_FIELD_MAPPING.md`。
- 不引入 SW 会员编码、COACH 扫描规则或一人一品牌档案的额外约束。活动品牌选择从现有授权范围，种子品牌从已有品牌身份中读取。
- 无统一全局审计可复用，因此只记录本模块必要操作，未扩展系统管理，也不改旧销售 Activity / 会员旅程。

## 前端模型（不是后端字段）

定义在 `src/types/marketing.ts`；演示种子只在 `src/mock/marketing-demo-data.ts`，用户变化只由 MarketingProvider / LocalStorage 保存。

| 集合 / 对象 | 关联与契约 |
| --- | --- |
| activities | 一个品牌、独立发布状态与四组时间；规则版本；嵌套活动 slots 与单个多项 pool |
| prizes | 中性奖品定义，供活动引用；不保存共享真实库存 |
| participations | activityId、冻结 subjectKey、已知身份引用快照、ACT 凭证、报名 / 签到 / 完成真实时间 |
| bookings | kind=ACTIVITY 或 PRIZE；participationId；PRIZE 另有 awardId / poolItemId；独立 slotId 与状态 |
| chances | 首次完成的发放流水，保存数量、时间与规则版本 |
| draws | 每次有效尝试含未中奖；唯一 operationId、发生时间、随机值、规则版本、可空中奖池项 |
| awards | 每次中奖对应的权益；WIN 凭证；当时名称 / 地点 / 说明 / 领取方式 / 有效期 / 规则快照 |
| audits | 动作、对象、操作人、真实时间、成功 / 拒绝、说明；不代替生产全局审计 |

## 身份判定与引用变化

1. user 必须存在、属于活动品牌且 `is_deleted === 0`。旧数据缺删除状态显示待核对，不自动当作有效或给旧档案补字段。
2. customer_id 非 NULL 且能找到现有 customer，采用 `customer:<id>`；否则采用 `user:<id>`。一个品牌可有多个 user，同一可靠 customer 在同一活动共用参与主体与一次机会发放。
3. 无可靠集团关联时，即使手机号 / UnionID 相同仍是独立 user；不按名称 / 手机号 / UnionID 合并或绑定。
4. 同活动查找冻结 subjectKey、已记录的 user 引用，以及这些可靠身份当前关联的 customer。关联变化后，原 user 或其当前集团的另一品牌档案仍复用原参与记录，不借新别名发新额度；原 subjectKey 不改。多条冲突参与主体阻止抽奖，留待核对，不合并。
5. 引用快照保存 userId / brand / openid / unionid。已知引用不存在、品牌改变、身份标识改变或有效状态不明时，显示待核对并阻止后续处理。即便 ID 被复用也不按姓名 / 手机号转给别人。
6. 独立会员重置若恰好保留完全相同身份标识，视作同一演示身份；真正悬空 / 改变的引用不会重绑。原型没有后端不可变身份世代 ID，真实身份恢复流程仍需后端设计。

历史记录留存；未知身份不会把已保存的成功事实改成0，只明确标注引用待核对。

## 状态、时间与完成

时区明确固定 Asia/Shanghai（UTC+08）。保存 ISO 实际时刻，企业时间输入转换为 +08:00，不随浏览器时区变化。窗口左闭右开：到截止时刻即拒绝。

发布状态 DRAFT / PUBLISHED / PAUSED / CANCELED，与预约、活动、抽奖、领奖时间阶段分别显示。活动结束不关闭有效奖品权益。

- 草稿允许未完整配置；发布验证必填、品牌、时间、地点、场次 / 截止 / 签到窗口、概率、次数、库存与履约容量。
- 关闭预约不要求虚构场次；关闭抽奖不要求奖池 / 次数 / 抽奖日期。线上只使用工作人员确认完成，无虚构入场签到。
- 发布后只允许修改名称、说明、封面；品牌、规则、概率、限额、原场次锁定。实质变更复制新草稿，复制不带参与或权益。仅可有记录地追加正配额 / 合法履约时段，不削减既有权益容量。
- PAUSED 停新活动报名 / 预约 / 改约及抽奖；已有活动预约可签到 / 完成。中奖者的奖品预约属于既有权益履约，可继续取消 / 重约 / 核销。
- CANCELED 二次确认展示未到场活动预约与权益数量；取消 BOOKED 活动预约，保留已签到、抽奖、奖品预约与获奖权益。取消不能恢复，需复制。已发布 / 有业务记录不能硬删除。
- 同主体一个有效活动预约；取消 / 改约必须在截止前。先验证目标再取消原记录，失败不丢原预约。签到后不释放容量，也不能自行取消 / 改约。
- BOOKED 仅在签到窗口结束后显示 NO_SHOW；不会在场次刚开始就判爽约，也不会放宽窗口冒充签到。
- 现场报名要求工作人员权限、配置允许、当前签到窗口及剩余容量。关闭预约的直接报名也创建参与记录，但不造场次。
- CHECKIN 完成条件仅在线下签到时首次自动完成；STAFF 签到后仍是参与中，再确认完成。线下必须先签到；重复签到 / 完成返回原结果，不增机会。

## 次数、概率、库存和核销

统一 `executeMarketing` 校验并产生一份下一状态；Provider 同步持有最新状态引用，先一次保存整份状态，再提交 UI。存储失败不提交结果、扣次、配额或局部记录。单页重复点击不能超额；不声称多设备 / 多标签事务安全。

- 获得 = chance 流水总量；已用 = draws 含未中奖次数；剩余 = 获得 − 已用。上限不是已获得，UI 的0明确显示0。
- 首次完成只发一次；默认2次机会 / 抽奖上限2 / 中奖上限1。每日上限可选，按企业自然日计算。中奖上限达成时剩余次数保留但不可用。
- 开启抽奖时次数 / 各上限正整数，发放≤累计上限；配额非负整数；各项概率0–100且加未中奖=100%。发布时有可中奖库存；同一奖品不重复占多个池项绕过个人上限。
- 正式演示使用 Math.random，不按身份指定中奖。测试注入确定性随机源与时钟，但不把测试结果伪装成生产抽奖。
- 先校验身份 / 权限 / 状态 / 完成 / 时间 / 次数 / 限额 / 库存。没有有效可中奖概率或库存时停止、不扣。普通未中奖保存一条 draw 并消耗一次。
- 库存耗尽或个人奖品上限对应的固定概率转为未中奖，不重新分配给其他项。
- operationId 与活动 / 主体绑定；保存过的请求原样返回，刷新重试不再调用随机源或扣次。失败没有孤立扣次。
- 库存：总配额 = 待履约占用 + 已发放 + 可抽。中奖即占用；核销占用→已发放，可抽不变。过期未领仍占用，不自动返池。
- 奖品预约属于一份具体 award，不重报名 / 不扣机会；最多一条有效预约，取消只释放时段。独立履约时段总容量≥配额；满额 / 截止 / 过期拒绝。
- ACT 凭证只用于签到 / 完成，WIN 只用于具体领奖。先识别品牌 / 用户 / 对象 / 场次 / 状态，再二次确认。校验角色、类型、地点、窗口及场次；预约型必须有有效奖品预约且在对应履约窗口。
- 重复核销返回原权益，不再发奖 / 扣库；不给普通操作员撤销已领奖入口。

## 范围与统计

复用现有角色：HQ_ADMIN 具有现有 GP/UN 范围，可管理 / 编辑奖池 / 核销 / 用户预览；分销商经理及销售无会员 / 营销品牌权限。没有另造核销员 / 品牌管理员账号。动作层显式分开 manage / redeem / preview 与只读；测试可注入有限范围验证，但不代表 UI 已新增角色。

先授权，再筛选、统计与下钻。私有详情 / 用户预览 / 凭证 URL 直达与写入均校验。“全部”只是授权范围。共享中性奖品库不是品牌客户数据。

八项活动指标来自同一 Store：当前有效活动预约主体、签到主体、完成主体、抽奖主体、draw 次数、中奖主体、award 份数、fulfilled 份数。预约取消历史不算当前有效；人数按 participation 去重，不用手机号。概览仅三项核心指标，其余在下方。所有指标打开相同活动 / 品牌 / 授权 / 查看时间的只读来源 ID 明细。数据或活动变化关闭旧明细，不把人数累加到集团人数 / 三视图概览。

## 存储、演示与兼容

营销命名空间 `kivisense-marketing-prototype-v1`，schema version=1，revision 保存操作版本。仅缺 namespace 初始化一次；刷新不重播种、改日期或覆盖用户修改。v1缺 revision 只在读模型取0，不重置；未知版本 / 集合 / 不可读内容保持原 LocalStorage，显示阻断和备份 / 明确重置提示，不默认为空数据0。

营销重置二次确认、仅替换自身键；销售 / 会员原重置行为不改，也不清营销。测试只用隔离 BrowserContext 的虚构数据，未触碰用户浏览器存储。

四个初始演示：预约工坊 + 工作人员完成抽奖；免预约现场活动；预约签到无抽奖；结束但仍领奖的活动。覆盖三种奖品方式、满场、未中奖、已领、过期、配额耗尽。历史结果是明确标注的虚构种子，不冒充真实抽奖；只有当前存在且有效的品牌 user 才会加入参与 / 历史权益种子。缺可用身份展示原因，不创建会员或销售客户。
